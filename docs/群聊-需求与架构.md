# 群聊（问问 TA、拉个群聊聊）· 需求与架构

日期：2026-11-25。状态：方案已定，尚未开发。与《产品与架构说明》《视觉规范 V3》配套。

**一句话**：现在只能问小四一个人。新功能让用户可以问有名的投资人；小四还能把几个人拉进一个群，围绕一只股票讨论，用户也能进去说话。

**前期目标是节目效果**：好看、吸引人、想接着看。不要求每句话都“有帮助”。

---

## 1. 已经定下来的

| 事项 | 决定 |
| --- | --- |
| 角色是什么 | 有成体系投资方法的人，每人一份扎实的人设（信条、看股票的顺序、不碰什么、说话方式）。不是“数据姐”“套牢哥”这类脸谱 |
| 首批角色 | 巴菲特（看公司）、Serenity（看产业链）、炒股养家（看情绪）、索罗斯（看宏观和预期） |
| 小四 | 主持人：开场、点名、拱火、收场。不再自己给观点 |
| 数据 | 谁都能调的工具：个股概率、财务、方法和方法的结果、大盘。**方法是数据，不是角色**；不做成绩单 |
| 约束 | 要松。**不做证据门控**，不因为格式或校验不过而报错。任何失败都变成一句台词，对话不能断 |
| 唯一的硬限制 | 每人每天的调用上限，只为管成本 |
| 模型 | DeepSeek |
| 从哪儿进 | 回答页上“拉他们进来聊聊”，话题就是刚问的那只股票 |
| 聊什么 | 第一版只围绕一只股票开场；开场之后用户说什么，角色都接 |
| 群的寿命 | 一个问题开一个群，聊完存成记录，可以回看、可以接着聊。群和群之间不共享记忆 |
| 谁来选人 | 默认四个人都拉进来，用户可以踢人、加人 |
| 角色页 | 前端加一页，告诉用户我们有哪些角色 |
| 架构 | 轻，但留好扩展口。不搬旧版四象智投的运行时 |

**第一版不做**：长图分享、每天自动开一场、用户自建角色、产业链数据、跨群记忆、自由话题开场。

**需要同步修改的旧约定**：《产品与架构说明》6.2 节写着“不安排角色之间为展示而对话”“协作流程固定为小四派发 → 专业角色取证 → 小四综合”。群聊与它不一致，以本文档为准：角色之间可以对话，流程由“导演”决定。原来的“问小四”结论页（引擎算、规则生成文字）保持不变，群聊是它旁边的新东西，不是替换。

## 2. 产品

### 2.1 用户看到的流程

1. 用户像现在一样问一只股票，看到结论页。
2. 结论页上有一个入口：**“拉他们进来聊聊”**，旁边是四个人的头像。
3. 点进去是群聊页。小四开场：一句话说今天聊什么，然后点第一个人。
4. 四个人依次发言，每条两三句话，一条一条冒出来，有“正在输入”。后说的人会接前面人的话。
5. 小四挑一处分歧拱火：“巴菲特，养家说你这套在 A 股不灵，你怎么看？”被点到的人回应，对方再回一句。
6. 一场戏到此停下，等用户。用户可以：
   - 直接说话，或者 @ 某个人问；
   - 点“接着聊”，让他们再来一场；
   - 踢人、加人；
   - 离开，以后从记录里回来。

### 2.2 好看靠什么

这几条是做提示词和导演策略时的判断标准。

- **每个人有成见。** 一开口就知道是谁。巴菲特永远先问“我懂不懂这门生意”，养家只问“有没有情绪”。
- **有冲突。** 四个视角看同一只股票本来就会得出不同结论。导演的职责之一就是找到分歧并放大。
- **节奏像真群聊。** 一条消息不超过三句。有引用回复、有抢话、有人只回一个“呵”。不是每人一篇报告。
- **用户能搅局。** 用户说的话角色会接，会叫他的名字。
- **甩数据有冲击力。** 角色说“我查了”，后面跟一张数据卡。

### 2.3 首批四个角色

| 角色 | 看什么 | 核心信条 | 天然的对手 |
| --- | --- | --- | --- |
| 巴菲特 | 公司 | 护城河、能力圈、好公司等好价格；不懂的不碰 | Serenity、养家 |
| Serenity | 产业链 | 绕开龙头，找上游最卡脖子的环节；机会藏在公开的碎片信息里 | 巴菲特 |
| 炒股养家 | 情绪 | A 股游资的打法：情绪周期、赚钱效应、只做龙头、错了就走 | 巴菲特、索罗斯 |
| 索罗斯 | 宏观和预期 | 反身性：价格会改变基本面；自己可能是错的，看到错误就是机会 | 所有确信自己正确的人 |

候补（第一版跑顺后一次加一个）：芒格、段永平、彼得·林奇、木头姐、利弗莫尔。

**已知缺口**：Serenity 的方法依赖产业链信息（谁给谁供货、哪一环产能紧），引擎里现在没有。第一版他靠模型自己知道的说，深度会不如另外三个。以后补一个产业链数据工具，不用改架构（见 3.4）。

### 2.4 小四怎么主持

小四有四种动作，由导演决定什么时候用：

| 动作 | 例子 |
| --- | --- |
| 开场 | “今天聊比亚迪。最近 20 天跌了 7%。巴菲特，你先说？” |
| 点名 | “Serenity，你一直没说话。” |
| 拱火 | “索罗斯，他说你那是马后炮。” |
| 收场 | “两边谁也没说服谁：一个看估值，一个看情绪。你站哪边？” |

小四说话短、有点皮，不下结论。

### 2.5 数据卡

角色调用了数据工具，消息下面就挂一张小卡片，内容由系统按工具返回的数据画，不由模型写。例如“和现在相似的时候，3 个月后在涨的有四成”这张卡，数字直接来自引擎。

这不是约束：模型嘴上说错了数，消息照样发出去。数据卡的作用是让“甩数据”有画面，也让想认真看的用户有个靠得住的东西。

### 2.6 页面

| 页面 | 地址 | 内容 |
| --- | --- | --- |
| 群聊页 | `/rooms/:id` | 顶部：话题（股票名、今天的价格）和成员头像；中间：消息流；底部：输入框、@ 选人、“接着聊” |
| 聊过的 | `/rooms` | 自己开过的群，按时间排。每条显示股票、参与的人、最后一句话 |
| 角色页 | `/personas` | 我们有哪些角色。每人一张卡：头像、名字、一句话介绍、看什么、三到五条信条、一句代表性的话、“拉 TA 聊聊” |
| 入口 | 结论页、看盘页 | “拉他们进来聊聊”按钮和四个头像 |

导航不加新项。“问小四”下面用页内切换（`SubNav`）挂三页：**提问 / 聊过的 / 角色**。

群聊在手机上是主要场景，页面按手机优先设计，PC 上居中一栏（最宽 760）。消息气泡、头像、数据卡的样式另行补进《视觉规范》。

**头像**：不用真人照片。第一版用带名字首字的图形头像，每人一个固定的颜色和图案；以后可以换成插画。

**角色页和群聊页顶部有一行小字**：“角色由 AI 按公开资料演绎，不代表本人。”

## 3. 技术架构

### 3.1 总的思路

**一个导演，一群演员，一条消息流。**

```
                        ┌──────────────────────────────┐
  用户说话 / 接着聊 ───▶ │  房间运行器（每个群一个）      │
                        │                              │
                        │   导演：下一步谁说、接谁的话   │
                        │      │                       │
                        │      ▼                       │
                        │   演员发言：一次模型调用       │──▶ 数据工具（引擎）
                        │      │                       │
                        │      ▼                       │
                        │   写进数据库 + 发到消息总线    │
                        └──────────────┬───────────────┘
                                       │
                                       ▼
                           SSE 推给所有打开这个群的页面
```

四条设计原则：

1. **失败即台词。** 任何一环出错（模型超时、工具报错、导演的输出解析不了、额度用完），用户看到的都是聊天里的一句话，或者这一条被悄悄跳过。接口不向前端抛错，页面不出现红色报错。
2. **发言是纯文本。** 不要求模型按 JSON 之类的固定结构说话。结构化的东西（谁说、回谁、挂什么卡）由导演和工具产生，不靠模型的输出格式。这是从“证据门控导致经常报错”里吸取的做法：对模型的输出没有格式要求，就没有格式错误。
3. **演出和观看分开。** 一场戏在后台跑，不依赖用户的页面连着。用户刷新、断网、换设备，回来接着看。
4. **只在四个地方留扩展口**：角色、数据工具、导演策略、模型。其他地方不做抽象。

### 3.2 模块

全部放在现有 Python 后端里，新增一个包 `backend/sixiang/room/`，不单独起服务。

| 文件 | 负责 |
| --- | --- |
| `personas.py` + `personas/*.md` | 角色表。读角色卡，提供“给模型看的人设”和“给用户看的介绍” |
| `tools.py` | 数据工具表。把引擎函数登记成模型能调用的工具 |
| `llm.py` | 模型接入。一个很薄的接口，后面是 DeepSeek |
| `director.py` | 导演。决定下一步；第一版只有“圆桌”一种策略 |
| `runner.py` | 房间运行器。按导演的决定执行，一条一条产出消息 |
| `bus.py` | 消息总线。运行器发，SSE 连接收 |
| `store.py` | 存取群和消息 |
| `prompts.py` | 拼提示词：群规 + 人设 + 话题简报 + 聊天记录 + 导演的提示 |
| `rehearse.py` | 彩排。命令行里跑一场戏，调提示词用 |
| `api/routes/rooms.py` | 接口 |

预计十个文件左右，每个几十到两百行。

### 3.3 角色

一个角色就是一个 Markdown 文件，例如 `personas/buffett.md`：

```markdown
---
id: buffett
name: 巴菲特
title: 伯克希尔的掌舵人
lens: 看公司
tagline: 好公司也要好价格
tools: [stock_financials, stock_outlook]     # 爱用的，不是限制
rivals: [serenity, yangjia]                  # 导演拱火时参考
temperature: 0.8
version: 1
---
## 信条
## 看一只股票的顺序
## 不碰什么
## 说话方式
## 和别人的典型分歧
## 示例发言
```

- 头部是给程序读的；正文六节是给模型读的人设。“示例发言”给三五条，模型学口气最管用。
- 角色页用的介绍（一句话、信条摘要、代表性的话）从同一个文件里取，不另存一份。
- `version` 每次改人设加一。每条消息记下当时的版本，方便回头看是哪一版人设说的。
- **扩展**：加一个角色就是加一个文件。以后用户自建角色，存在数据库里，实现同一个“取角色”的接口即可，其余代码不用动。

写人设的要求：以本人公开的文字为准（股东信、书、访谈、帖子），动笔前先把材料找来读，不凭印象写。Serenity 是 2026 年才出名的，尤其要先查资料。

### 3.4 数据工具

每个工具登记四样东西：名字、给模型看的说明、参数、处理函数。处理函数返回三样：

| 返回 | 给谁 | 说明 |
| --- | --- | --- |
| `text` | 模型 | 几句大白话，带上关键数字。模型据此说话 |
| `card` | 前端 | 数据卡的类型和数据。可以没有 |
| `ok` | 运行器 | 失败时为假，`text` 里写“这次没取到”，模型自己圆 |

处理函数**不许抛异常**，出错就返回 `ok=False`。

第一版的工具，全部包装现有的引擎函数，不新写计算：

| 工具 | 回答什么 | 来自 |
| --- | --- | --- |
| `stock_outlook` | 这只股票接下来一段时间涨的可能多大；相似的时候后来怎样；最坏的十分之一 | `analysis.distribution.analyze` |
| `stock_recent` | 最近的涨跌、成交量、离高点低点多远 | 日线 |
| `stock_financials` | 市盈率、市净率、营收和净利润增长、负债率 | `store.financials` |
| `option_outlook` | 这个期权费回本的可能 | `analyze`（带期权费） |
| `method_hits` | 这只股票今天符合方法库里的哪几种方法；这些方法历史上灵不灵 | 方法库 |
| `market_outlook` | 大盘现在什么状态，接下来涨的可能 | 问大盘 |
| `compare_stocks` | 两只股票对着看 | 两只对比 |

- 所有角色都能调所有工具。角色卡里的 `tools` 只是“爱用的”，写进提示词里引导，不做限制。
- 一条发言里最多调两次工具（防止来回查个没完，纯粹为了节奏和成本）。
- 同一个群里同样的调用结果缓存起来，后面的人再查是瞬间的。
- **扩展**：加一个工具就是登记一条。产业链数据、新闻、解禁、外部 MCP 以后都按这个方式加，角色不用改就能用上。

### 3.5 模型接入

`llm.py` 只暴露一个能力：给一串消息和一组工具，流式返回文字和工具调用。

- DeepSeek 提供与 OpenAI 兼容的接口，用 `httpx` 异步请求直接调，不引入额外的 SDK。（`httpx` 目前只在开发依赖里，要提到正式依赖。）
- 配置都走环境变量，写在仓库根目录的 `.env` 里：

  | 变量 | 说明 |
  | --- | --- |
  | `SIXIANG_LLM_API_KEY` | 密钥 |
  | `SIXIANG_LLM_BASE_URL` | 默认 DeepSeek 的地址 |
  | `SIXIANG_LLM_MODEL` | 演员用的模型 |
  | `SIXIANG_LLM_DIRECTOR_MODEL` | 导演用的模型，默认同上 |
  | `SIXIANG_ROOM_DAILY_LIMIT` | 每人每天最多多少条角色发言 |

  具体的模型名和参数以 DeepSeek 官方文档为准，接入时再核对，不在这里写死。
- 没配密钥时，群聊入口不显示，其他功能不受影响。
- 超时和重试：单次调用设超时；失败重试一次；还不行就交给“失败即台词”（3.9）。
- **扩展**：换模型或者给不同角色用不同模型，只改配置。测试用一个“假模型”，按剧本吐字，不联网。

### 3.6 导演

导演回答一个问题：**现在该干什么？** 它看着群的当前状态，返回下一步：

| 下一步 | 含义 |
| --- | --- |
| 某个角色发言 | 带一句提示：轮到你了 / 回应某人的某句话 / 用户问你了 |
| 小四做一个动作 | 开场、点名、拱火、收场 |
| 停，等用户 | 这场戏演完了 |

第一版的策略叫“圆桌”，规则很简单：

1. **开场**：小四开场 → 四个人各说一条（顺序按“对手挨着坐”排，后一个人最容易接前一个的话）。
2. **拱火**：小四挑一处分歧 → 被点的人回应 → 对手回一句。
3. **停**，等用户。到此大约 8 条消息。
4. **用户说话后**：@ 了谁就谁回；没 @ 就由导演挑一到两个最该接话的人。回完就停，最多 3 条。
5. **用户点“接着聊”**：再来一轮拱火（第 2 步），换一处分歧。

导演有两处需要“判断”，各用一次便宜的模型调用：挑哪处分歧来拱、用户这句话该谁接。这两次调用让模型回一个很短的答案（比如只回两个名字）。**解析不了就退回固定规则**：拱火按角色卡里的 `rivals` 配对轮着来，接话按上一个发言的人。导演永远给得出下一步。

每场戏有消息条数上限（上面的 8 条和 3 条），是为了节奏，也是为了不让一个群无限烧钱。

- **扩展**：导演是一个接口，“圆桌”是它的一种实现。以后的“辩论赛”（两人对打，用户投票）、“一对一”（只问一个人）、“每天自动开一场”，都是新的实现，运行器不用改。

### 3.7 一条发言是怎么产生的

1. 运行器从导演那里拿到“某角色发言 + 提示”。
2. 先发一个“正在输入”事件。
3. 拼提示词（见 3.8），带上工具表，调模型，流式接收。
4. 模型想查数据：执行工具，把 `text` 还给模型继续说；有 `card` 就记下来。最多两轮。
5. 文字边生成边推给前端。
6. 说完：存进数据库，发“消息完成”事件，带上数据卡。

### 3.8 提示词怎么拼

从上到下五层：

| 层 | 内容 | 谁写 |
| --- | --- | --- |
| 群规 | 这是一个群聊；每条不超过三句；说人话；可以反驳、调侃、引用别人；想甩数据就调工具；不替别人说话 | 所有角色共用一份 |
| 人设 | 角色卡正文 | 每个角色一份 |
| 话题简报 | 聊的是哪只股票、今天的价格、最近的涨跌。开群时取一次，所有人共用 | 代码生成 |
| 聊天记录 | 最近约 30 条原文；更早的压成一段摘要 | 代码生成 |
| 导演的提示 | “现在轮到你。小四刚问你：……”或“回应索罗斯的这句话：……” | 导演 |

聊天记录按群聊的样子写给模型：每条前面带名字，自己说过的话标成自己的。

聊得很长时，更早的部分用一次模型调用压成摘要存在群上，之后不再重复发送全文。

软性的要求（比如“这是历史统计，别替用户做买卖决定”）只写在群规里，一句话，不做拦截和过滤。

### 3.9 失败即台词

| 出了什么事 | 用户看到的 |
| --- | --- |
| 工具取数失败或超时 | 角色照常说话，可能说一句“我手头没数，凭感觉说两句” |
| 模型调用超时或出错 | 重试一次；还不行，这一条跳过，导演让下一个人说 |
| 模型说到一半断了 | 已经说出来的部分保留，当作说完 |
| 导演的判断解析不了 | 退回固定规则，用户无感 |
| 模型返回的内容很怪（空的、特别长） | 空的跳过；太长的截到三句 |
| 今天的额度用完 | 小四说“今天聊到这儿，明天接着来”，输入框停用 |
| 页面的连接断了 | 自动重连，从断开的那条接着收 |
| 服务重启，戏演到一半 | 群标记为“被打断”；用户回来时显示“接着聊” |
| 没配模型密钥 | 群聊入口不出现 |

所有这些情况都记日志，方便事后看哪里常出问题，但不给用户看。

### 3.10 演出和观看分开

**为什么**：如果让“生成消息”挂在用户页面的那条连接上，用户一刷新，戏就断了；两个页签同时开着，还会生成两遍。

**怎么做**：

- 每个群同一时间只有一个运行器（后台任务）。开群、用户说话、点“接着聊”都只是往这个群的信箱里放一个指令，运行器醒来处理。
- 运行器每产出一条消息：先写数据库，再发到消息总线。
- 页面通过 SSE 连到这个群。连上时先把数据库里已有的消息补发，再接着收新的。每条事件有序号，断线重连时带上“我收到第几条了”。
- 用户在一场戏中间说话：当前这条说完，导演下一步就处理用户的话，不会等整场演完。

**现状和边界**：线上是单进程 uvicorn，所以消息总线和运行器都放在进程内存里就够了，不需要 Redis。以后要开多进程时，把消息总线换成 Redis 的发布订阅、给运行器加一把跨进程的锁，接口不变。消息总线为此单独放一个文件。

**同步和异步**：现有后端是同步写法（引擎计算、数据库）。群聊里，模型调用用异步；引擎和数据库的调用放进线程池执行，不改现有代码。

**部署时要改一处**：nginx 反代 SSE 需要关掉缓冲（对群聊的流式接口设 `proxy_buffering off`，或者接口返回 `X-Accel-Buffering: no` 头），否则消息会攒成一坨才到。

### 3.11 存储

两张新表，写法和现有的表一致（放在 `auth/db.py`，启动时自动创建，SQLite 和 MySQL 都不用手动迁移）。

**rooms（群）**

| 字段 | 说明 |
| --- | --- |
| id、user_id | |
| topic_json | 话题。第一版是 `{"kind": "stock", "code": …}`；`kind` 留给以后的大盘、方法、自由话题 |
| title | 显示用的标题，如“比亚迪” |
| persona_ids_json | 现在群里有谁 |
| status | 空闲 / 演出中 / 被打断 |
| summary | 更早聊天记录的摘要 |
| created_at、updated_at | |

**room_messages（消息）**

| 字段 | 说明 |
| --- | --- |
| id、room_id、seq | `seq` 是群内序号，SSE 续传用 |
| role | 小四 / 角色 / 用户 / 系统（如“某某被请出了群”） |
| persona_id | 哪个角色 |
| text | 说的话 |
| reply_to | 回的是哪一条 |
| cards_json | 挂的数据卡 |
| meta_json | 模型、耗时、用了多少 token、人设版本、数据版本、有没有出过错 |
| created_at | |

**额度**：每人每天的角色发言条数，直接从 `room_messages` 按天数出来，不另建表。量大了再加计数表。

### 3.12 接口

| 接口 | 作用 |
| --- | --- |
| `GET /api/personas` | 角色列表（给角色页和头像用） |
| `POST /api/rooms` | 开一个群。传话题，可选传成员。立刻返回，开场在后台开始 |
| `GET /api/rooms` | 我聊过的 |
| `GET /api/rooms/{id}` | 群的信息和全部消息 |
| `GET /api/rooms/{id}/stream` | SSE。带 `Last-Event-ID` 时从那条之后续传 |
| `POST /api/rooms/{id}/say` | 用户说话，可带 @ 谁 |
| `POST /api/rooms/{id}/continue` | 接着聊 |
| `POST /api/rooms/{id}/members` | 拉人、踢人 |

SSE 的事件种类：

| 事件 | 含义 |
| --- | --- |
| `typing` | 某人正在输入 |
| `delta` | 某条消息新冒出来的几个字 |
| `message` | 一条消息说完了（含数据卡） |
| `scene_end` | 这场戏演完了，可以说话或“接着聊” |
| `members` | 成员变了 |

没有“错误”事件。

### 3.13 成本

一场开场戏大约是：导演判断 1 次 + 小四 2 条 + 角色 6 条，共约 9 次模型调用。聊天记录会越来越长，所以越往后每次调用越贵，摘要（3.8）就是为了压住这个。

控制成本的手段，按先后：

1. 每场戏的消息条数上限。
2. 每人每天的发言条数上限（`SIXIANG_ROOM_DAILY_LIMIT`）。
3. 早期聊天记录压成摘要。
4. 话题简报和工具结果在群内缓存。

每条消息的 `meta_json` 里记了 token 数，上线后能算出真实的单场成本，再回来定上限的具体数字。

### 3.14 测试和调试

- **假模型**：按剧本返回文字和工具调用，不联网。单元测试全用它。
- **必测的几件事**：圆桌的完整一场；用户中途插话；每一种失败都变成台词而不是异常（3.9 的每一行一个测试）；断线续传；额度用完。
- **彩排**：`python -m sixiang.room.rehearse --code sz002594` 在命令行里用真模型跑一场，直接打印对话。调人设和群规主要靠它，不用开页面。节目效果好不好，只能靠多跑、多看、多改提示词。
